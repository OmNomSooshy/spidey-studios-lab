# Mission 001 — Project Lightsaber return report

**Mission status: ACTIVE.** Management confirms the app installed, loaded a real Proffie-compatible font, and produced a promising first SmoothSwing experience. Human Ears then reported an audible jump during speed/direction changes and perceptible response delay. The source audit, cadence correction, regression traces, and replacement APK are now delivered. The cause of the remaining audible jump and Human Ears acceptance remain unresolved.

## Human Ears fidelity correction checkpoint

The previous version is [still available](https://github.com/OmNomSooshy/spidey-studios-lab/releases/download/lightsaber-bdb2b56-4-1/Project-Lightsaber-debug.apk). The replacement is [downloadable here](https://github.com/OmNomSooshy/spidey-studios-lab/releases/download/lightsaber-e5ee474-6-1/Project-Lightsaber-debug.apk). Management's report is direct physical-device evidence that the prior APK, real-font import, ignition, hum, and motion-driven swing were runtime reachable; the replacement needs the same listening regression.

**CONFIRMED — sensor-to-engine cadence defect.** The old Android adapter requested `SENSOR_DELAY_GAME`, received callbacks on the registering UI looper, and the native engine retained only the newest gyro values. `render()` then called the three-sample filter once per 256-frame audio block (~5.8 ms), repeating the latest value on blocks with no new sensor event and losing any intermediate sensor events. This differed from pinned `SmoothSwingV2::SB_Motion`, which filters each motion event. The engine now transports timestamped frames through a bounded single-producer/single-consumer queue and updates the filter once per received sample. Queue drops are counted and exposed in diagnostics.

**CONFIRMED — avoidable configured delay.** The previous app requested the nominal 20 ms `SENSOR_DELAY_GAME` cadence and requested a 1024-frame AudioTrack buffer (23.2 ms at 44.1 kHz, unless Android's reported minimum was larger). The corrected app requests 5 ms sensor sampling with zero batching, dispatches sensor events on a dedicated handler thread, renders 128-frame blocks (~2.9 ms), requests a buffer of at least two blocks (256 frames/~5.8 ms, unless the platform minimum is larger), and runs its renderer at Android's audio thread priority. These are configuration changes, not measured end-to-end latency results.

**UNRESOLVED — cause of the audible jump.** The C++ transition targets match a test-only transcription of the pinned Proffie V2 equations over 770 timestamped events and six A/B transition swaps. That narrows the defect but does not prove the perceptual cause. The event-loss/cadence mismatch could make the rendered target trajectory coarser than Proffie; the replacement corrects that mismatch. Actual sample-boundary, font timbre, and device mixer contributions still require Human Ears on the replacement build.

**CONFIRMED source semantics.** Pinned `SB_Motion` uses the magnitude `sqrt(gyro.y² + gyro.z²)` and subtracts that nonnegative speed from its transition position. It does not use angular-velocity sign to reverse transition travel. The Android implementation preserves this; a physical direction reversal changes speed magnitude only as the motion changes. No separate reverse-direction sound behavior has been added.

**PCM observation — INFERRED risk, cause unresolved.** The pinned SmthJedi paired swing files are mono PCM at 44.1 kHz and 284,288 frames (6.446 s). Their first sample is zero, but end samples vary (up to 13,843 PCM counts in the inspected files), so repeating an individual file can have a nonzero waveform edge. Proffie calls `PlayOnce` then `PlayLoop(effect->GetFollowing())`; Android repeats the selected WAV directly and does not port the complete `Effect` following/file-reader behavior. A loop-edge jump is therefore plausible, but not confirmed as Proffie-equivalent or as the cause of Management's motion-transition report. No loop crossfade was added without source evidence.

**Latency still unmeasured.** The app now displays requested/actual AudioTrack buffer frames, estimated app-queued frames in milliseconds, AudioTrack underrun count, and received/processed/dropped gyro events. The queued-frame estimate excludes downstream device/HAL/speaker latency. Only a physical-device measurement can establish end-to-end response.

## Proffie source comparison

The relevant upstream chain is `SmoothSwingV2::SB_Motion` in `sound/smooth_swing_v2.h`, settings in `sound/smooth_swing_config.h`, pair/effect discovery in `sound/effect.h`, font state/effects in `sound/hybrid_font.h`, and the playback/ramp path through `sound/buffered_wav_player.h`, `sound/playwav.h`, and `sound/volume_overlay.h`. Local C++ re-expresses behavior; it does not copy or compile ProffieOS files.

| Behavior | Classification | Comparison |
|---|---|---|
| Gyroscope filter and event timing | **ADAPTED WITH DOCUMENTED DIFFERENCE** | Proffie `BoxFilter<Vec3,3>` is fed on every `SB_Motion` event (and can be prefilled when `clear` is set). Core averages the same three-sample Y/Z window, with a safe zero/partial warm-up. The previous latest-sample atomics caused dropped/repeated samples; the replacement SPSC queue restores one filter update per received sensor event. Android still adapts coordinate mapping and does not reproduce Proffie's `clear` signal. |
| Swing speed | **PRESERVED** | Both use `sqrt(y² + z²)` in degrees/second after filtering (`hypot` in C++). Android converts radians/second and supplies event timestamps; there is no absolute-position estimate. |
| Activation and continuation | **PRESERVED** | Entry at `SwingStrengthThreshold`; an active swing continues down to `0.9 × threshold`. Core resets activity when the blade is off. |
| Sensitivity and sharpness | **PRESERVED** | `min(1, speed/SwingSensitivity)` followed by `pow(strength, SwingSharpness)`. Core reads matching numeric keys from V2 `smoothsw.ini`. |
| Maximum swing volume | **ADAPTED WITH DOCUMENTED DIFFERENCE** | Proffie multiplies shaped strength by `MaxSwingVolume`; core uses the same gain parameter, followed by its Android-oriented 0.5 base gain and soft limiter. Per-effect `SFX.*` volume metadata is not implemented. |
| Hum ducking | **PRESERVED** | Core applies `1 - shaped_strength × MaximumHumDucking/100`, now using shaped strength as the source path does. Font-level hum gain and basic hum-start/delay settings are applied by the mixer. |
| Paired low/high selection | **ADAPTED WITH DOCUMENTED DIFFERENCE** | Core selects a random index and keeps low/high files paired and phase-aligned. It accepts modern and legacy naming, several numbered layouts, and reports missing/unreadable partners. Proffie’s full `Effect` selection/no-repeat semantics and count diagnostics are not replicated. |
| Angular transition and low/high blend | **PRESERVED IN SOURCE-DERIVED TEST TRACE; RUNTIME SOUND STILL UNRESOLVED** | Core uses Proffie's `A.rotate(-speed*delta)`, `while (A.end()<0) { B.midpoint=A.midpoint+A.separation; Swap(); }`, and clamped `-A.begin()/A.width`. A test-only transcription of the pinned source matches the core at each of 770 deterministic motion updates, including six role swaps. `VolumeOverlay` source sets a 2 ms default ramp; Android uses sample-domain float ramps of the same duration. This verifies equations and target gains, not perceptual equivalence or output scheduling. |
| Swing playback timing | **ADAPTED WITH DOCUMENTED DIFFERENCE** | Loop starts use the current hum position when `ProffieOSSmoothSwingHumstart` requests it, otherwise a monotonic-time offset; the same random pair is used. Core reads PCM16 into memory and loops/resamples by linear interpolation. It does not port `BufferedWavPlayer` prebuffering, stream scheduling, all Proffie WAV encodings/rates, or every effect offset/variant. |
| Ignition/retraction | **ADAPTED WITH DOCUMENTED DIFFERENCE** | Source semantics were checked and corrected: Proffie ignition is `out`/`poweron` (with variants); retraction uses `in` and optionally `pstoff`, or power-off fallbacks. Core follows those primary names, pairs `in` then `pstoff` if present, and applies simple hum start/fade configuration. It does not reproduce all `hybrid_font.h` sequencing, fast/alternate variants, or the embedded fade scheduler. |

The table describes source/code comparison, not proof of identical sound. Whether adapted transitions and timbre feel right remains **UNRESOLVED SOURCE SEMANTICS** until listening on the target phone. Proffie’s audio scheduler, buffered stream, storage reader/locks, board clock/random helpers, amplifier sequencing, and embedded sensor stack are hardware/platform dependencies replaced by app-private files, JNI, Android SensorManager/AudioTrack, and a portable C++ renderer. A complete transitive upstream source build/link closure has not been enumerated.

## Platform adapter decision

**PLATFORM ADAPTER DECISION — Godot 4.6.3 + OpenXR + Godot OpenXR Vendors 5.1.0.** Godot was selected for its documented Android/OpenXR deployment path, native GDExtension C++ integration, and a vendor-maintained Meta `XR_FB_passthrough` wrapper. The vendor addon documentation says passthrough starts automatically when the OpenXR interface selects alpha blend; the app requests that mode and enables the Meta passthrough extension. The project uses the Compatibility renderer, matching the vendor's Meta passthrough sample. This remains a source/configuration finding until Quest runtime inspection.

The app calls the existing `project-lightsaber/core/src/saber_engine.cpp` through a native `SaberAudioStream`/`SaberAudioPlayback` GDExtension. The audio playback's Godot `_mix()` callback renders the shared engine's stereo signed-16 PCM in bounded 512-frame chunks, converts it to `AudioFrame`, and uses `AudioServer`'s mix rate. Audio sample production is independent of rendered frame cadence. The engine is neither forked nor reimplemented for Quest. Font extraction and `SaberEngine::loadFont()` are separate from output mixing. The Android project, importer, core files, and Spider Byte are unchanged by Mission 002.

## Controller tracking and mapping

The action map selects `/interaction_profiles/meta/touch_controller_plus` and binds the right grip pose plus right A/B clicks. Godot maps the public `grip_pose` action name to tracker pose `grip`; the `XRController3D` uses tracker `right_hand`, pose `grip`. A visible one-metre emissive cylinder is attached to that node, extending along local `-Z`; it is shown after ignition and hidden on retraction or tracking loss.

**CONFIRMED — source:** the pinned Godot 4.6.3 OpenXR implementation calls `xrLocateSpace()` in `play_space` at the predicted display time and copies the returned `XrSpaceVelocity.angularVelocity` components into `XRPose.angular_velocity`; OpenXR specifies angular velocity in radians/second. `XRPose.transform` and this velocity share that tracking reference frame. `XRPositionalTracker.set_pose()` emits `pose_changed` for new samples and `pose_lost_tracking` on loss. The adapter subscribes to `pose_changed`, accepts only the `grip` pose while `has_tracking_data` is true, transforms velocity through the inverse grip basis, maps local longitudinal `-Z` to engine X and local transverse X/Y to engine Y/Z, then converts radians/second to degrees/second. This is a Quest-specific mapping decision and is not copied from the phone adapter.

**CONFIRMED limitation:** Godot's `XRPose` exposes no runtime sensor timestamp and no angular-velocity-valid bit. The app timestamps each fresh grip `pose_changed` callback with `Time.get_ticks_usec()` converted to nanoseconds; it does not poll and repeat cached samples, and does not derive angular velocity from pose differences or substitute controller linear velocity. The precise Touch Plus grip-axis convention, delivered sample cadence, and velocity-valid behavior need a physical headset check. On tracking loss the app retracts and stops submitting motion rather than reusing stale motion.
